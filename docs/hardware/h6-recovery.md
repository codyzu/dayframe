## Proposed staged trial requiring specific approval

The hardware plan requires an ADR/scope decision and independently approved installation/configuration. This is a new engine and profile, not an extension of the earlier exact helper installation approval. The proposal below is concrete and reversible app work; it includes no system/firmware, Home-default, router or ADB change. A phase only proceeds after the previous phase's stop/acceptance gates pass.

1. **Preflight and side-by-side installation.** Recheck exact identity, Firefox/helper versions, existing DF and Home preference XML, accepted H2 record, available storage (APK is about 140 MiB), reviewed APK/hash/signer and absence of this package. Install this APK normally without `-g`, then verify installed version/ABI/full APK readback digest and unchanged Home preferences. Do not clear, uninstall, copy or patch Firefox/profile/Rootless/helper. Save private evidence and stop at an unexplained mismatch.
2. **Manual native rendering and maintenance.** Open only the new launcher activity, configure the existing public frame URL through normal UI, and first verify the unauthenticated/provisioning state. Grant only this app's `SYSTEM_ALERT_WINDOW` through normal Android UI if the owner approves the trial; never repair app-ops or accessibility through root. Enable its supervision, leaving its boot toggle off and existing helper startup on. Check the actual full-surface native/provisioning state (all four dashboard modes follow provisioning in phase 3), native DK, the independent service process/overlay and retained old DF/Firefox fallback. Owner physically tests native DK/two-finger menu, stock Home → Settings → DK → kiosk return. If the direct Settings/Wi-Fi action is rejected, retain the native menu and use stock Home, recording the limitation. Do not inject a gesture and label it physical acceptance.
3. **Read-only provisioning/session persistence.** Reuse the existing scoped display key only through this origin's normal `/setup` page in the new profile; no key in a URL, admin login, cookie database copy or raw credential logs. Verify actual full-surface Morning/Photos/Home/Night rendering and protected photo paint, then deliberate page reload/session replacement and one controlled app restart without data clearing. Confirm no repeated unauthorized reload loop. Stop on access mismatch; do not mint/revoke credentials as remediation. New native cookie/profile evidence must be measured independently of the accepted Firefox profile.
4. **Bounded faults in this package only.** After physical exit/fallback passes, verify actual main/supervisor/renderer process names, UIDs/PIDs/start times and a foreground, healthy private `health.json`. Test one renderer death, one main-process death and one main UI stall, individually, with read-only sampling and screenshots. Only signal a freshly revalidated `dev.dayframe.kiosk` main PID or its `:tabN` renderer; never Android, Firefox, the existing helper, Rootless or the supervisor. For a stall, use `SIGSTOP` on only the selected trial PID, with an independent host deadline and `SIGCONT` cleanup if it remains the same process. Observe actual recovery rather than manually launching the app to mask failure. Require new main PID or increased session generation, matching private health PID/state, a repainted dashboard and usable native maintenance. Record time from fault/usable network-clock to recovery and whether the supervisor stayed alive. Limit each observation to two minutes, stop on a mismatch and use the accepted Firefox/DF fallback if recovery fails.
5. **Load-stall/paint lifecycle distinction.** A renderer stall while healthy exercises missing page heartbeats; a reload in that stalled renderer can separately exercise the 45-second load watchdog. The normal native page reload retains the session; a deliberately replaced session is a different operation. Native paint-reset/repaint during an actual Settings round trip must not create a reload storm. Record genuine engine callbacks/health transitions and screenshots. Pure policy calls or an early first-paint callback do not prove a load/paint test. If safe fault targeting or verification is unavailable, record an explicit blocker/fallback and leave the case open; do not add a broad JavaScript command bridge or root/system workaround.
6. **Force-stop/manual fallback.** Force-stop only the trial package, explicitly expecting Android to stop its receiver/supervisor/overlay together. Verify the independently retained old DF/Rootless/Firefox path and relaunch the kiosk manually; confirm its saved consent/config/profile return. Label manual recovery honestly. A same-package service cannot bypass Android's force-stopped state. No repeated automated launch loop or privileged grant is proposed.
7. **Optional approved startup migration, only after native gates pass.** Through normal UI, disable only the accepted helper's startup toggle, retain its package/profile/fallback, and enable the new kiosk boot toggle. Then one specifically approved normal Android reboot and one owner-operated cold cycle can establish the new package's early-clock gate, DK/supervisor startup, protected-photo persistence and no-touch foreground behavior. Compare Home XML/grants and actual browser/package identity; do not count the earlier Firefox boot tests as GeckoView evidence. Restore the accepted helper immediately on failure. Network/late-Wi-Fi/clock manipulation and earlier deferred interruption/soak tests are not included by implication.
