# Fullscreen and GeckoView kiosk plan

**H5 in progress; H6 planned.** The [H5 execution record](h5-fullscreen.md) covers the deployed manifest, approved Rootless/helper updates, passed pre-boot physical return and the observed normal/cold-boot authentication failure. Earlier H4 omissions remain deferred; H6 is optional if H5 meets household needs. A native wrapper needs a separate ADR under the web-app specification's native-app non-goal. It does not change the Astro/Workers architecture or €0 service budget.

## What upstream actually supplies

At reviewed commit `e97c50ba459c49ea8237259f69b95cd28054b628`, the [Modern10 report](https://github.com/wesbos/photo-frame-dashboard/blob/e97c50ba459c49ea8237259f69b95cd28054b628/docs/dragontouch-modern10-charm.md) contains a 14 October follow-up describing a contributor's GeckoView **143.0.20251003115653**, ARMv7 kiosk. It reports boot startup, five-second load retries, a physical two-finger hold (1.5 s), launcher/Settings navigation, and two days of operation. One blank-white display required improved stalled-load and lost-paint recovery. Root ADB persisted after reboot; accessibility enablement dropped after force-stop. An isolated install-over test did not drop it; reboot alone was not isolated.

**Source availability:** the reviewed tree contains `dashboard/kiosk/src/com/wesbos/homehq/MainActivity.java`, `NavigationService.java`, `AndroidManifest.xml`, build scripts and README. `MainActivity` imports `android.webkit.WebView`, not GeckoView; the manifest has an opt-in HOME alias and no BootReceiver. No GeckoView implementation or dependency for the contributor's variant was found in the reviewed tree. We need to request a public source link in a future authorized upstream interaction, or independently implement the described design. No message or upstream PR is authorized by this planning work.

The available WebView wrapper supplies ideas for fullscreen, saved URL, touch maintenance menu, navigation service and load retries. It is not the reported GeckoView app. No upstream code is imported: license coverage remains unresolved (no LICENSE/COPYING file found at this revision). Resolve licensing before copying. See [provenance](sources.md).

## H5: incremental fullscreen evaluation

Current execution: [H5 fullscreen shortcut](h5-fullscreen.md). Manifest/icons are deployed at `3763694`, stock launcher was rechecked, and the owner approved the exact Rootless trial. Standalone Firefox has been observed at 1280 × 800 with existing protected photos, and the owner passed two physical Home/Settings/shortcut return loops. The approved normal reboot retained the second-page shortcut but stopped at the Home chooser without DF; its cookie was later found expired in 1971. Approved normal-setup reuse of the existing key restored photos, with correct October 2027 expiry and successful Firefox-only restart persistence. The owner then performed cold power: startup again reached Home chooser without DF and the cookie again expired in 1971. Fresh retained logs show Firefox starting through its WorkManager boot receiver with a January 1970 clock before clock correction. The exact cookie-write path is not instrumented; the owner confirmed physical fullscreen return, while private photos needed access. Existing-key recovery restored the running display; the owner approved and executed the source-verified browser cookie-cap preference trial and one additional cold cycle. Cookie expiry remained in October 2027 despite repeated early Firefox startup with the wrong clock; the owner’s physical fullscreen/Photos confirmation is pending. The sequence below retains the original incremental gates; it does not undo these executed results.

After H4, inspect whether Dayframe serves an appropriate manifest and Firefox offers **Add to Home screen** on the existing launcher. The upstream demo's fullscreen/landscape manifest is not evidence that Dayframe has equivalent metadata; the initial pre-H5 repository inspection found no web app manifest. The implemented metadata and actual Classic measurements above now supply that evidence.

In a separately approved session, create the shortcut, open it by touch, measure usable viewport and observe Android bars, Back/Home and exit behavior. Verify the read-only cookie/profile used by the shortcut. Keep stock home as default. If the launcher cannot host shortcuts, stop this route before installing Rootless; optional launcher evaluation is a new explicit action after recording undo and proving physical navigation. Do not edit `launcher.db` just because upstream did. Later approved reboot/cold-power tests must measure launch time, clock correction, manual fallback and whether the shortcut survives. H5 does not claim automatic boot merely because it is fullscreen.

## H6 design and work packages

1. **Decision/build gate:** confirm H5 shortfalls, source/license availability, official Mozilla Maven artifact existence for pinned version, ARMv7 native library and minimum SDK compatibility with API 23. Inspect the actual 143 AAR/API docs; current online Javadocs describe newer versions and are not a compile contract for 143. Verify artifact checksums/signatures/dependency graph, keep lock/version evidence and release signing key private. Independently authored shell should use its own package ID. No paid build/update service.
2. **Minimal shell:** one landscape immersive activity with a persistent Gecko profile and allowlisted Dayframe HTTPS origin. Reject arbitrary external schemes, file/content URLs and untrusted intent URLs; do not bypass TLS errors or expose broad native JS bridges. Retain display-only authentication; no admin credentials. Provide an offline/retrying screen with last status and manual recovery.
3. **Profile/session lifecycle:** reuse one runtime, own session/view lifetimes, close old sessions on replacement, preserve cookies deliberately and confirm `/setup` → display authentication through app restarts. Never log keys/cookies. Denial must show reprovisioning rather than an endless unauthorized reload loop. Apply existing private-photo retention rules.
4. **Load recovery:** track navigation start, completion (`ProgressDelegate.onPageStop(success)`), failure and a finite load timeout (initial proposal 30–60 s, tune on hardware). First contentful paint may be only a background: do not cancel watchdogs on that callback. Investigate `ContentDelegate.onPaintStatusReset` plus visibility/lifecycle state to detect missing painted content without resetting on every normal transition. Recreate a session only on confirmed failure; avoid reboot loops. Add a page-level ready/heartbeat signal constrained to our origin if needed to distinguish successful navigation from a failed app render.
5. **Network/time recovery:** connectivity callbacks accelerate retry; bounded backoff with jitter (proposal 5 s up to 60 s) avoids download storms. Keep a single scheduled retry, cancel obsolete ones after success and clean up callbacks. The H5 cookie metadata specifically requires investigating clock readiness **before runtime/profile cookie initialization**, not only delaying page navigation or retrying after a TLS failure. Its repeated near-epoch cookie timestamps and corrected-clock restart pass are evidence. Fresh cold logs now directly show the WorkManager receiver starting Firefox before clock correction; the exact cookie rewrite call path is uninstrumented. Retry on clock correction/resume; recompute Dayframe date/schedule after large wall-clock jumps. Certificate errors remain blocking; never accept an invalid certificate. Upstream PR #138 is a useful unmerged WebView proposal with incomplete TLS-path testing, not a GeckoView implementation.
6. **Boot startup:** evaluate a manifest `BOOT_COMPLETED` receiver with required permission, explicit launch target and Android 6 behavior. Preserve stock HOME while testing; the contributor's boot-receiver route differed from upstream's opt-in HOME alias. Test installed/first-launched state, ordinary restart, cold boot, delayed Wi-Fi and vendor foreground competition. Force-stopped packages may not receive boot broadcasts until manually launched; document recovery. Native process death is distinct from page failure: prove relaunch behavior or add a separately reviewed watchdog rather than assuming a page timer survives process death.
7. **Maintenance:** native menu with Reload, Wi-Fi/Android Settings, Back to dashboard and Exit to a known launcher. A deliberate physical gesture should work on the actual touch controller; injected two-contact gestures are not proof. Test return from settings by touch with Android bars absent. If accessibility navigation is necessary, request minimal permissions and preserve other enabled services; do not overwrite the whole accessibility list. Require explicit approval for grants/settings. Check service health after install, force-stop and reboot. Keep independent maintenance ADB until an alternative is demonstrated.
8. **Acceptance:** reproduce H4 rendering/auth/48-hour checks, plus repeated Wi-Fi loss, load stall, blank-render recovery, renderer/session failure, process death, boot with late network/time and physical exit/return. Proposed target: recovery within two minutes of valid network/time returning, no sustained reload loop, usable navigation and no unbounded process/session/memory growth. Capture exact conditions and elapsed times; disable ADB only after H7's independent path gate.

A WebView `onPageFinished` callback cannot simply be renamed into a correct GeckoView completion strategy. Test each failure independently on the pinned engine. Two reported stable days on Modern10 do not establish long-term Classic 10 reliability.
