# ADR 0003 — M4 administration and display credentials

Status: implemented locally; production activation and actual-device acceptance pending.

## Decision

Keep Cloudflare Access as the final human identity mechanism: two individually allowlisted email identities, RS256 verification at the Worker, a one-hour maximum JWT age, and no password database. Access protects `/admin/*`; the Worker authorizes every private API independently. Access headers alone never establish identity. Admin recovery is independent of the home network.

Use one SQLite-backed `Administration` Durable Object, named `household`, for settings and the active display credential. Photos remain in KV. The object is accessible only through a binding; its internal URLs have no public router. Every operation uses a storage transaction. The Worker does not cache credential decisions. After a successful rotation/revocation response, subsequent authorization checks reject the previous credential. An already authorized request can finish. No KV propagation window applies to this state.

The rejected alternative was storing revocation state in KV: its eventual consistency cannot establish a strict short revocation deadline. Adding an authoritative object is justified specifically for credential revocation and serialized settings writes; it does not introduce photo counters or coordinate photo mutations.

Generate 256 random bits server-side. Return the hexadecimal key once to an authenticated admin; store only SHA-256, issuance and expiry. One frame credential is supported, matching the single-frame scope. Rotation replaces it atomically; failed/lost issuance responses are recovered by another rotation. Keys expire after 365 days; no silent renewal. The admin transfers the key privately and enters it into `/setup` on the home network. That page exchanges it for a host-scoped, `Secure`, `HttpOnly`, `SameSite=Strict`, `/api` cookie with the remaining lifetime. The key never enters a URL, localStorage, bundle, telemetry, or persisted browser JavaScript state. The setup input is cleared immediately; the admin key panel is cleared on hide/page exit. Browser cookie limits or manual data clearing can shorten persistence and require reprovisioning.

Every display read and exchange requires both the key and a matching `CF-Connecting-IP`. `HOME_NETWORKS` is a private Worker secret: exact IPv4 addresses, optional IPv6 addresses or prefixes /48–/128, comma-separated (at most eight entries). Missing/invalid configuration fails closed. This is defense in depth, not device identification. Never accept an arbitrary forwarded header. Cloudflare must supply the client address; local tests explicitly emulate this trusted boundary. Disable Pseudo IPv4's header-overwrite mode if IPv6 checks are needed. Cloudflare network-header behavior must be checked at activation.

Persist only validated household display settings. Admin GET/PATCH `/api/config` supports management; read-only GET `/api/config/display` exposes an explicit settings whitelist. Neither contains network addresses, credential digests, admin identities, Access configuration, or tokens. Missing fields use public defaults; PATCH merges supplied fields into existing settings in a transaction. Reject unknown keys, malformed values, invalid IANA timezones, coordinates outside their ranges, invalid/overlapping schedules (including across midnight), zero-length periods, and unsafe durations. Intervals are half-open; adjacent periods are valid. Gaps are allowed, with Morning as the planned M5 fallback. Bad persisted records fail closed. Schedule and override settings are persisted now; resolving and running them remains M5.

Authorized dashboard startup loads settings without persisting them in browser storage, then uses the chosen location/timezone for weather/clock and saved fit/interval for photos. Public visits and failed settings loads use public example defaults. A reload applies changes; background configuration refresh is M5. Weather cache keys include coordinates/timezone to prevent cross-location reuse.

## Privacy and logout

Private responses use `private, no-store`, with no shared or service-worker cache. Slideshow images exist as at most two in-memory blob URLs. An authorization failure, mode exit, hide, or page exit clears them. Offline continuity is bounded to five minutes after the last successful authorized catalog/image response, then images are cleared and network authorization retried. A responsive page enforces that timer; a suspended browser cannot run timers until resumed and clears on its hide/resume lifecycle. A compromised device can copy already delivered bytes; revocation cannot erase them remotely.

Admin galleries verify sessions every 30 seconds, remove previews on observed denial, and bound offline previews to five minutes plus the 30-second check interval. Page exit removes previews. Logout clears the display cookie even when expired/revoked; human logout uses Access logout. Uploaded source files and retry closures stay only in the original admin tab while it remains open. Expiry stops the batch and leaves each unattempted file with an explicit retry after reauthentication in another tab. No automatic mutation retry occurs.

## Cost gate and failure policy

Reviewed 16 October 2026: [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) permits SQLite objects on Workers Free: 100,000 requests/day, 13,000 GB-s/day, 5 million rows read/day, 100,000 written/day and 5 GB storage. On Free, exceeding a limit fails operations. [KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/) remains relevant to photos only. No paid plan, upgrade, add-on or usage billing is authorized by this ADR.

One display at 20 seconds uses approximately 4,321 image authorizations plus 288 catalog authorizations/day, plus startup/session checks; each requires one object read. Two admins with a continuously open photo tab add at most 5,760 session requests/day combined. State is a single small record, written only by explicit settings/key changes. There are no alarms, sockets, polling inside the object, or background work. Requests await short storage transactions; inactive objects may hibernate. Quotas are account-wide and abuse can exhaust them. Object outages fail display authorization/settings with 503; independently verified admins can still use photo APIs. No paid fallback exists. Production account-plan and observed CPU/duration validation remain activation gates, not claims from local emulation.

Wrangler includes the SQLite migration and binding in local and production config. The ignored production config generator preserves both alongside the private photo namespace. No deployment has been performed for M4.
